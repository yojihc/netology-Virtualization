### 2. Распределение ресурсов по 3 нодам

Для обеспечения высокой доступности (High Availability) нагрузка распределяется по трем изолированным серверам (нодам) следующим образом:

| Ресурс / Компонент | Нода 1 (Node 1) | Нода 2 (Node 2) | Нода 3 (Node 3) |
| :--- | :---: | :---: | :---: |
| **База данных** | 1 копия | 1 копия | 1 копия |
| **Система кеширования** | 1 копия | 1 копия | 1 копия |
| **Бекенд (Backend)** | 4 копии | 3 копии | 3 копии |
| **Фронтенд (Frontend)** | 2 копии | 2 копии | 1 копия |
| 📊 **Итого CPU на ноду** | **6.4 ядра** | **5.4 ядра** | **5.2 ядра** |
| 💾 **Итого RAM на ноду** | **10.5 ГБ** | **9.9 ГБ** | **9.85 ГБ** |

---

### Краткое описание архитектурного решения

1. **Отказоустойчивость хранения (Stateful):** Главное условие конфигурации — распределение 3-х копий Базы данных и Кэша строго по одной на каждую из 3-х нод. Это исключает единую точку отказа. При выходе из строя любого одного сервера, оставшиеся две ноды сохраняют кворум (2/3 копий живы), что позволяет кластеру автоматически выбрать нового лидера и продолжить работу без потери данных.
2. **Параметризация чарта (Мультиокружение):** Так как приложение упаковывается в Helm-чарт для деплоя в разные контуры, все параметры из первой таблицы (количество реплик, лимиты CPU и RAM) вынесены в переменные. это позволяет для «тяжелого» Production использовать конфигурацию на 3 ноды, а для «легких» окружений (Dev/Stage) уменьшать количество копий (например, до 1 реплики на компонент) ради экономии физических ресурсов.
