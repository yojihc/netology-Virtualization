# Домашнее задание к занятию «Микросервисы: подходы»

Вы работаете в крупной компании, которая строит систему на основе микросервисной архитектуры.
Вам как DevOps-специалисту необходимо выдвинуть предложение по организации инфраструктуры для разработки и эксплуатации.


## Задача 1: Обеспечить разработку

Предложите решение для обеспечения процесса разработки: хранение исходного кода, непрерывная интеграция и непрерывная поставка. 
Решение может состоять из одного или нескольких программных продуктов и должно описывать способы и принципы их взаимодействия.

Решение должно соответствовать следующим требованиям:
- облачная система;
- система контроля версий Git;
- репозиторий на каждый сервис;
- запуск сборки по событию из системы контроля версий;
- запуск сборки по кнопке с указанием параметров;
- возможность привязать настройки к каждой сборке;
- возможность создания шаблонов для различных конфигураций сборок;
- возможность безопасного хранения секретных данных (пароли, ключи доступа);
- несколько конфигураций для сборки из одного репозитория;
- кастомные шаги при сборке;
- собственные докер-образы для сборки проектов;
- возможность развернуть агентов сборки на собственных серверах;
- возможность параллельного запуска нескольких сборок;
- возможность параллельного запуска тестов.

Обоснуйте свой выбор.

### Ответ: 

| Критерий / Требование | Yandex Managed GitLab | GitHub Cloud + Actions | TeamCity Cloud |
| :--- | :--- | :--- | :--- |
| **Облачная система (SaaS/Managed)** | Да (полностью обслуживается Yandex Cloud) | Да (SaaS) | Да (SaaS) |
| **Репозиторий на каждый сервис** | Да (структура Projects / Groups) | Да | Да (через привязку внешнего Git) |
| **Запуск по кнопке с параметрами** | Да (интерфейс `Run pipeline` + переменные) | Да (`workflow_dispatch`) | Да (Custom build со спец-параметрами) |
| **Шаблоны конфигураций сборок** | Да (директива `include` и шаблоны CI/CD) | Да (Reusable Workflows) | Да (Build Templates) |
| **Безопасное хранение секретов** | Да (CI/CD Variables + Yandex Lockbox) | Да (GitHub Secrets) | Да (HashiCorp Vault / Текстовые шифры) |
| **Собственные Docker-образы** | Да (поддержка `image: my-custom-image`) | Да (`container: image`) | Да (Docker-оболочки для шагов) |
| **Агенты на собственных серверах** | Да (подключение легковесных **GitLab Runner**) | Да (Self-hosted Runners) | Да (Build Agents) |
| **Параллельные сборки и тесты** | Да (через параллельные стадии, `parallel` и матрицы) | Да (matrix strategy) | Да (параллельные конфигурации) |

Обоснование: Выбранный комплекс на базе Yandex Managed Service for GitLab является оптимальным решением, поскольку он предоставляет единую All-in-One платформу для хранения кода и управления CI/CD в рамках единого облачного периметра компании, полностью закрывает требования по безопасности и шаблонизации пайплайнов через нативный синтаксис .gitlab-ci.yml, поддерживает нативную интеграцию с секретами Yandex Lockbox и позволяет эффективно распределять тяжелые нагрузки по параллельному тестированию на собственные изолированные серверы с помощью легко администрируемых агентов GitLab Runner.

## Задача 2: Логи

Предложите решение для обеспечения сбора и анализа логов сервисов в микросервисной архитектуре.
Решение может состоять из одного или нескольких программных продуктов и должно описывать способы и принципы их взаимодействия.

Решение должно соответствовать следующим требованиям:
- сбор логов в центральное хранилище со всех хостов, обслуживающих систему;
- минимальные требования к приложениям, сбор логов из stdout;
- гарантированная доставка логов до центрального хранилища;
- обеспечение поиска и фильтрации по записям логов;
- обеспечение пользовательского интерфейса с возможностью предоставления доступа разработчикам для поиска по записям логов;
- возможность дать ссылку на сохранённый поиск по записям логов.

Обоснуйте свой выбор.

### Ответ:


| Критерий / Требование | Наш стек (Vector + Kafka + OpenSearch) | Стек ELK / EFK (Fluentd + Elasticsearch) | Grafana Loki Стек (Promtail + Loki) |
| :--- | :--- | :--- | :--- |
| **Централизованное хранилище** | Да (Кластер OpenSearch в Yandex Cloud) | Да (Кластер Elasticsearch) | Да (Хранилище Loki / Object Storage) |
| **Сбор из stdout (минимальный overhead)** | Да (Vector читает напрямую логи Docker/K8s) | Да (Fluentbit / Fluentd читает stdout) | Да (Promtail собирает логи контейнеров) |
| **Гарантированная доставка логов** | **Экстремальная** (Kafka как буфер + Vector диск-кэш) | Средняя (Fluentd буфер на диске, при сбое ES логам тяжело) | Средняя (Зависит от доступности инжекторов Loki) |
| **Поиск и полнотекстовая фильтрация** | Высший уровень (Lucene движок индексации) | Высший уровень (Lucene движок индексации) | Ограниченный (Поиск по лейблам, медленный grep по тексту) |
| **Интерфейс и доступ для разработчиков** | Да (OpenSearch Dashboards / Kibana с RBAC) | Да (Kibana с разграничением прав) | Да (Grafana с разграничением прав) |
| **Ссылка на сохранённый поиск** | Да (Полноценный URL со всеми фильтрами и таймфреймом) | Да (Сохранение запросов через Kibana Short URLs) | Ограниченно (Ссылки на панели Grafana Explore) |

Обоснование: Выбранный стек на основе Vector, Managed Apache Kafka и OpenSearch является оптимальным решением, поскольку он гарантирует стопроцентную доставку логов без потери данных при любых пиковых нагрузках за счет архитектуры с промежуточным брокером сообщений, минимизирует утилизацию ресурсов на целевых серверах благодаря сверхбыстрому агенту сбора Vector, предоставляет разработчикам мощный инструмент полнотекстового поиска с возможностью шаринга постоянных ссылок на срезы логов.

## Задача 3: Мониторинг

Предложите решение для обеспечения сбора и анализа состояния хостов и сервисов в микросервисной архитектуре.
Решение может состоять из одного или нескольких программных продуктов и должно описывать способы и принципы их взаимодействия.

Решение должно соответствовать следующим требованиям:
- сбор метрик со всех хостов, обслуживающих систему;
- сбор метрик состояния ресурсов хостов: CPU, RAM, HDD, Network;
- сбор метрик потребляемых ресурсов для каждого сервиса: CPU, RAM, HDD, Network;
- сбор метрик, специфичных для каждого сервиса;
- пользовательский интерфейс с возможностью делать запросы и агрегировать информацию;
- пользовательский интерфейс с возможностью настраивать различные панели для отслеживания состояния системы.

Обоснуйте свой выбор.

### Ответ:


| Критерий / Требование | Наш стек (Prometheus + Grafana) | Стек Zabbix | Стек ELK / Elastic Metrics |
| :--- | :--- | :--- | :--- |
| **Централизованный сбор метрик** | Да (Модель Pull / Скрепинг по расписанию) | Да (Модель Push через агентов) | Да (Через Metricbeat в Elasticsearch) |
| **Метрики ресурсов хостов** | Да (Через стандартный Node Exporter) | Да (Через Zabbix Agent) | Да (Через System модуль Metricbeat) |
| **Метрики ресурсов сервисов** | Да (Через cAdvisor / Kubelet для контейнеров) | Ограниченно (Сложные кастомные скрипты) | Да (Через Docker/Kubernetes модули) |
| **Кастомные/специфичные метрики** | Высший уровень (Библиотеки Prometheus SDK) | Средний уровень (Кастомные UserParameter) | Хороший уровень (Интеграция с APM) |
| **Интерфейс для запросов и агрегации** | Экстремальный (Гибкий и мощный язык PromQL) | Средний (Встроенные вычисляемые элементы) | Хороший (Языки KQL и ES DSL) |
| **Панели и кастомизация (Dashboards)** | Высший уровень (Гибкие, динамические дашборды) | Средний уровень (Статичные комплексные экраны) | Хороший уровень (Kibana Dashboards) |

Обоснование: Выбранный стек на основе Prometheus и Grafana является стандартом для микросервисной архитектуры, поскольку он идеально закрывает все требования по многоуровневому сбору метрик, а также предлагает лучшую на рынке визуализацию со сквозной кастомизацией панелей для инженерных команд.
